## 1. Objectif

Lire les vidéos en **720p** quand YouTube l'expose à `yt-dlp`, sans jamais casser :

- la lecture actuelle en **360p progressif** (format `18`), qui doit rester le repli garanti ;
- la **reprise** locale (position SQLite, seek différé quand la durée est connue) ;
- les **beacons** de progression (`cpn`, `playback`, `atr`, `watchtime`, `final=1&state=paused`).

Contraintes inchangées : Linux/Wayland, Slint 1.19, libmpv par API render (jamais `--wid`),
UI et messages en français, identifiants et chemins en anglais, aucun secret dans le dépôt
ni dans un log, aucun appel réseau sur le thread UI.

## 3. Mesures du 2026-11-20/21 (machine réelle)

### 3.1 Ce qui marche : HLS `web_safari` sur `dQw4w9WgXcQ`

Commande :

```bash
yt-dlp -J --no-warnings --no-playlist --no-progress \
  -f 'b[height<=720]' \
  --extractor-args 'youtube:player-client=web_safari' \
  'https://www.youtube.com/watch?v=dQw4w9WgXcQ'
```

Résultat mesuré :

- `format_id=95`, `protocol=m3u8_native`, `height=720`, `duration=213`,
  `vcodec=avc1.4D401F`, `acodec=mp4a.40.2`, `requested_formats=[]` (flux **combiné**).
- `-F` liste `91`–`96` en `m3u8`, dont `95` = **1280×720**.
- Manifeste : `HTTP 200 application/vnd.apple.mpegurl`, 59 217 octets.
- Premier segment : `HTTP 200`, 827 576 octets.
- `ffprobe` : `h264 1280x720` + `aac`.
- `mpv --start=42 --frames=1` :
  `DUR=00:03:33 WIDTH=1280 HEIGHT=720 POS=00:00:42 SEEKABLE=yes`, code de sortie 0.
- `yt-dlp` journalise `[jsc:deno] Solving JS challenges using deno` puis
  `Downloading m3u8 information` pour cette vidéo.

Conclusion : le HLS `web_safari` est **lisible par mpv, avec son, sans PO token**, et la
durée est exposée (`213 s`), donc `pending_seek` dans `main.rs` s'appliquera.

### 3.2 Ce qui ne marche pas : la disponibilité n'est pas générale

Échantillon testé le 2026-11-21 avec `--extractor-args 'youtube:player-client=web_safari'` :

| Vidéo | Résultat `web_safari` |
|---|---|
| `dQw4w9WgXcQ` | formats `91`–`96` + `18`, dont **95 = 720p** |
| `9bZkp7q19f0` | **storyboards seulement** (`sb0`–`sb3`), aucun format vidéo |
| `kJQP7kiw5Fk` | storyboards seulement |
| `fJ9rUzIMcZQ` | storyboards seulement |
| `jNQXAC9IVRw` | `ERROR: No video formats found!` |
| `aqz-KE-bpKQ` | storyboards seulement |
| `M7lc1UVf-VE` | storyboards seulement |
| `ysz5S6PUM-U` | storyboards seulement |

Donc **1 vidéo sur 8** exposait le 720p HLS. Le HLS doit être traité comme une
**opportunité**, pas comme le chemin principal.

### 3.3 Le repli 360p actuel est intact

```bash
yt-dlp -J --no-warnings --no-playlist --no-progress \
  -f 'b[height<=720][protocol^=http]/b[height<=720]/b' \
  --extractor-args 'youtube:player-client=web,web_embedded' \
  'https://www.youtube.com/watch?v=9bZkp7q19f0'
```

→ `format_id=18`, `protocol=https`, `height=360`, `requested_formats=[]`.
C'est exactement ce que fait le code actuel (`crates/youtus-play/src/ytdlp.rs`).

### 3.4 Piège important : la liste de clients ne fusionne pas les formats

Testé `--extractor-args 'youtube:player-client=web_safari,web'`, avec le tiret **et** le
souligné, dans les deux ordres, sur `9bZkp7q19f0` :

- le log ne montre que `Downloading web safari player API JSON` ;
- la liste ne contient **que les storyboards**, pas le format `18` du client `web`.

Autrement dit, `web_safari,web` dans un seul appel **ne sert à rien** : il faut
**deux invocations séparées** de `yt-dlp`.

### 3.5 Autres clients testés (sans PO token)

- `mweb` → format `18` 360p uniquement.
- `ios` et `tv` → aucun format exploitable (pas de PO token / DRM).
- Aucun `cookies.txt` sur la machine ; la session WEB signée n'a donc pas pu être mesurée.
- `yt-dlp --version` : `2026.10.26` ; `PO Token Providers: none` ; `Plugin directories: none`.

## 4. Stratégie retenue

1. **Premier appel** : `web_safari` seul, sélecteur HLS d'abord :
   `b[height<=720][protocol^=m3u8]/b[height<=720][protocol^=http]/b[height<=720]/b`.
2. **Si le premier appel échoue** (format indisponible, storyboards seulement,
   `No video formats found`, JSON illisible…) : **deuxième appel** avec le code actuel,
   `web,web_embedded` et le sélecteur progressif
   `b[height<=720][protocol^=http]/b[height<=720]/b`.
3. Si les deux échouent, remonter l'erreur du second appel (c'est le chemin que
   l'utilisateur connaît).
4. Un flux HLS est **combiné** : `audio_url = None`, ne pas appeler `add_audio`.
5. Ajouter `protocol` à `ResolvedStream` pour que le log et les tests disent
   explicitement `hls` ou `https`.
6. **Ne pas** ajouter `bgutil` ni de dépendance PO token dans cette étape.
   C'est une option à proposer à l'utilisateur seulement si le 720p général devient exigé
   (voir §8).

Pseudo-code cible dans `crates/youtus-play/src/ytdlp.rs` :

```rust
pub fn resolve(video_id: &str, max_height: u32, cookies: Option<&Path>) -> Result<ResolvedStream, Error> {
    let hls = resolve_with(
        video_id,
        max_height,
        cookies,
        "b[height<={max_height}][protocol^=m3u8]/b[height<={max_height}][protocol^=http]/b[height<={max_height}]/b",
        "youtube:player-client=web_safari",
    );
    match hls {
        Ok(stream) => Ok(stream),
        Err(_) => resolve_with(
            video_id,
            max_height,
            cookies,
            "b[height<={max_height}][protocol^=http]/b[height<={max_height}]/b",
            "youtube:player-client=web,web_embedded",
        ),
    }
}
```

`resolve_with` reprend le corps actuel de `resolve` (construction de `Command`,
gestion de `YtDlpMissing`, extraction du dernier ligne de stderr, `parse`).

## 6. Pièges mesurés (ne pas les redécouvrir)

- **Liste de clients** : `web_safari,web` n'essaie pas le second client et ne fusionne pas
  les formats. Il faut deux commandes.
- **Storyboards** : quand `web_safari` ne rend pas de vidéo, il rend `sb0`–`sb3`.
  Un sélecteur qui ne filtre pas `mhtml` les choisirait ; garder `protocol^=m3u8` en tête.
- **Flux HLS combiné** : `requested_formats` est vide ; `audio_url` doit rester `None`.
- **mpv et les en-têtes** : `accept` est écarté car sa valeur contient une virgule ;
  l'UA passe par la propriété `user-agent`. Le HLS a été lu avec ces en-têtes.
- **Seek** : `start` est refusé par mpv après initialisation ; la reprise reste appliquée
  dans `main.rs` dès que `duration > 0`. Le HLS expose bien 213 s.
- **Beacons** : le ping `final` part de façon synchrone dans le worker à la fermeture ;
  ne pas déplacer cette logique sur le thread UI.
- **Client TV** : `/player` TV répond `UNPLAYABLE` ; la progression et la lecture restent
  en client WEB. Ne pas « corriger » ça en changeant de client.
- `/tmp/youtus/` de la session précédente a disparu (redémarrage). Les artefacts
  (`safari.json`, `manifest.m3u8`, `manifest.headers`) sont à refaire si besoin ;
  le serveur de beacons est désormais versionné dans `scripts/beacon-server.py`.

## 8. Décision ouverte : comment obtenir du 720p **général**

Le HLS `web_safari` ne suffit pas pour toutes les vidéos. Si l'utilisateur exige le 720p
partout, il faudra choisir, **avec lui**, entre :

1. **Livrer le 720p opportuniste** (ce document) et mesurer le taux de disponibilité sur
   ses abonnements réels. C'est le plus petit changement et il ne casse rien.
2. **Cookies** : importer un `cookies.txt` WEB et relancer les mesures. Le plumbing existe
   déjà (`--cookies`, `Config::cookies_path`, sonde) ; aucun cookie n'est disponible
   aujourd'hui, donc le gain n'est pas prouvé. Les cookies débloquent aussi l'attribution
   à l'historique et les commentaires.
3. **PO token via `bgutil-ytdlp-pot-provider`** : serveur Node/Deno local + plugin yt-dlp,
   puis DASH 720p avec le client `web`. Non installé, `Plugin directories: none`.
   Cela ajoute un démon à faire tourner à côté de l'app : ne pas l'installer sans accord
   explicite de l'utilisateur.

Ne pas réimplémenter SABR/PO token dans Rust : `yt-dlp` reste la seule source d'URL.
